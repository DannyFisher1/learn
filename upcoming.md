
## Requirements Document: LangGraph Visual Debugger/Monitor (Phase 1)

**Version:** 1.0
**Date:** 2025-05-05 *(Self-correction: Use current date)*

**1. Introduction**

*   **1.1 Purpose:** To provide a dedicated interface within the application for developers to visualize the real-time execution flow of the backend LangGraph agent. This tool aims to enhance understanding of the agent's decision-making process, facilitate debugging by showing state changes and tool interactions, and allow inspection of the data flowing through the graph.
*   **1.2 Scope (Phase 1):**
    *   **In Scope:**
        *   A new, distinct page/route within the Next.js application (e.g., `/debugger`).
        *   Displaying a visual representation of the application's primary LangGraph structure (currently defined in Python).
        *   An input mechanism to initiate graph runs via the existing `/ask-stream` endpoint.
        *   Real-time processing of the `astream_log` data streamed from the backend.
        *   Visual highlighting of the currently active node(s) on the graph canvas during execution.
        *   A dedicated area to display the sequence of messages (Human, AI, Tool) constituting the agent's state (`AgentState.messages`) as it evolves during the run.
        *   Displaying details of initiated tool calls (tool name, arguments).
        *   Displaying the results (observations) returned by tools.
        *   Displaying the final text output generated by the agent upon completion.
        *   A mechanism to stop/abort an ongoing graph run.
        *   Displaying basic error information if the stream or graph execution fails.
    *   **Out of Scope (Phase 1):**
        *   Visual graph *editing* or creation (nodes/edges are based on the Python definition).
        *   Saving/loading different graph definitions.
        *   Advanced debugging: Breakpoints, step-by-step execution control, manual state modification.
        *   Node configuration via the UI (e.g., changing prompts).
        *   Persistence of run history (beyond the current session's display).
        *   Integration with external tracing platforms (like LangSmith, though the backend might still use it).
*   **1.3 Target Audience:** Developers and engineers working on the application's agentic backend.
*   **1.4 Definitions:** (Same as previous document: IDE, LangGraph, Node, Edge, State, SSE, `astream_log`, React Flow)

**2. Functional Requirements (FR)**

*   **FR-DBG-001 (Debugger Route):** The system *shall* provide a distinct web page accessible via a specific route (e.g., `/debugger`).
*   **FR-DBG-002 (Static Graph Display):** The debugger page *shall* render a visual representation of the primary LangGraph's nodes (e.g., "agent", "action") and edges using a graph visualization library.
*   **FR-DBG-003 (Run Initiation):** The system *shall* provide a user interface element (e.g., text input and button) to submit a query that initiates a run of the LangGraph via the `/ask-stream` endpoint.
*   **FR-DBG-004 (Stream Processing):** The frontend *shall* connect to the `/ask-stream` SSE endpoint and process the incoming `astream_log` data chunks.
*   **FR-DBG-005 (Node Highlighting):** The system *shall* update the visual representation of the graph in real-time to indicate the currently executing node(s) based on start/end events parsed from the stream.
*   **FR-DBG-006 (Message Log Display):** The system *shall* display the sequence of `HumanMessage`, `AIMessage`, and `ToolMessage` objects from the agent's state (`AgentState.messages`) as they are updated via the stream. The display should clearly differentiate message types.
*   **FR-DBG-007 (Tool Call Detail Display):** When a tool call is initiated (detected from an `AIMessage` or specific log event), the system *shall* display the tool's name and input arguments in a designated area.
*   **FR-DBG-008 (Tool Result Detail Display):** When a tool result is returned (detected from a `ToolMessage` or specific log event), the system *shall* display the result/observation content, associated with the corresponding tool call.
*   **FR-DBG-009 (Final Answer Display):** When the agent generates its final textual response (detected via streamed tokens or the final `AIMessage`), the system *shall* display this complete response clearly.
*   **FR-DBG-010 (Run Control):** The system *shall* provide a mechanism (e.g., a "Stop" button) to cancel the current graph run and disconnect the SSE stream.
*   **FR-DBG-011 (Error Indication):** The system *shall* display error messages received from the stream or connection failures.

**3. Non-Functional Requirements (NFR)**

*   **NFR-DBG-001 (Performance):** Real-time UI updates (highlighting, state changes) should be visually smooth and responsive to incoming stream events.
*   **NFR-DBG-002 (Clarity):** The visualization of the graph flow and the presentation of state/tool data must be clear and easy for a developer to interpret.
*   **NFR-DBG-003 (Responsiveness):** The UI should remain interactive even while processing the stream.
*   **NFR-DBG-004 (Reliability):** Gracefully handle stream interruptions or malformed data where possible, logging errors.

**4. Technical Requirements**

*   **TR-DBG-001 (Frontend Framework):** Next.js (React)
*   **TR-DBG-002 (UI Components):** shadcn/ui (or consistent library)
*   **TR-DBG-003 (Graph Visualization):** **React Flow** library
*   **TR-DBG-004 (State Management):** React state (`useState`, `useEffect`, `useCallback`, `useRef`).
*   **TR-DBG-005 (Styling):** Tailwind CSS
*   **TR-DBG-006 (Backend API):** Must use the existing `/ask-stream` endpoint, which streams detailed `astream_log` data correctly.
*   **TR-DBG-007 (Stream Parsing):** Frontend (`lib/api.ts` and `debugger/page.tsx`) MUST correctly parse the `astream_log` `ops` data to identify node start/end events, message updates (`AIMessageChunk`, `AIMessage` with tool calls, `ToolMessage`), and extract relevant details for visualization (node IDs, message content, tool info). *(We implemented the parser in `lib/api.ts` in the previous steps)*.
*   **TR-DBG-008 (Graph Structure Source):** For Phase 1, the graph node/edge structure displayed on the frontend can be **hardcoded** in `debugger/page.tsx` to match the known Python graph structure. *(The optional `/graph-structure` endpoint is deferred)*.
